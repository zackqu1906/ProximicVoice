# 编辑候选方案研究（2026-09-17，未接入产品）

可以让 LLM 提出最多 2～3 个修改方案，再由用户选择；目前项目没有候选列表或可信的候选置信度。推荐只在存在真实歧义时请求选择，明确的纠错仍直接完成，避免每句话多一次操作。

## 现有能力

- `text_processing/edit_tool.py` 只定义单个修改结果：片段分支返回 `original_text` 和 `modified_text`，全文分支只返回 `modified_text`。
- `edit_response.py` 会拒绝未定义字段。仅在提示词中要求返回 `candidates` 会破坏当前返回格式，不能直接上线。
- `llm.py` 的两路竞速采用两种输出格式，先得到有效且不同于原文的结果就应用。另一路保留用于记录。两个结果可能相同，也没有按正确概率排序。
- `LLMBranchTrace` 记录结果、耗时、校验及错误等信息，没有置信度；当前请求也未采集 token 概率。

## 可行方案

方舟 Responses API 支持自定义函数调用。基于此，可以另行设计一个返回候选数组的工具，让一次请求生成 1～3 个有不同含义或修改位置的候选。这是应用层方案，不依赖接口原生提供 N-best；本次没有验证当前具体模型是否支持 `n` 或 `logprobs` 参数，也没有启用候选接口。[方舟工具调用文档](https://www.volcengine.com/docs/82379/1958524?lang=zh)

建议每个候选包含原文中的准确目标、替换内容和简短展示说明。程序检验目标存在、修改范围正确，并按应用后的完整文本去重。只改一处时必须有唯一定位信息，不能把重复片段直接交给当前的全局字符串替换。

例如原文是“上午三点开会，下午三点培训”，用户仅说“四点”，可以展示：

1. 上午四点开会，下午三点培训。
2. 上午三点开会，下午四点培训。

另提供“保持原文 / 取消”。不要为凑第三项而擅自增加“全部替换”；用户明确说全部时应直接处理。又如“界面”对应“街道的街面包的面”已经明确给出“街面”，无需再列出“界面、街面、见面”让用户重复确认。

实现时，必须等用户选定之后才写入文本框、记录成功修改和建立撤销关联。候选生成和用户选择期间仍遵守当前的语音互斥流程；选定、取消或报错后再恢复下一句。此次没有改变这些流程或绑定新的手势。

## “置信度接近”不能直接作为现成条件

需要区分三个量：模型生成的自评分、单个 token 的概率、整个修改符合用户意图的概率。它们不相等。即便接口提供 token 概率，也不能把某个字或第一个 token 的概率当作整条修改的正确率。

已有研究发现，模型口头表达的置信度与内部 token 概率只有部分一致；另有研究在特定问答数据集上发现，口头自评分可优于条件概率。这说明自评分可以研究，但不能未经本项目数据验证就解释为“90% 正确”。这些研究没有直接验证当前模型的中文语音编辑场景。[ACL 2024](https://aclanthology.org/2024.acl-long.20/)、[EMNLP 2023](https://aclanthology.org/2023.emnlp-main.330/)

因此建议第一版不展示置信度百分比。先综合明确的位置歧义、词语歧义、不同分支结果是否冲突等信号来决定是否提供选择；模型返回的“需要选择”标记也只是信号，不是正确性保证。同一模型的两路答案一致，同样不证明它们正确或相互独立。

后续用用户确认的数据评估：首选正确率、前三项覆盖率、无意义候选比例、不必要的选择次数、错误自动应用率和延迟。若确实需要分数阈值，应在独立验证集上校准，并在更换模型后重新验证。

## 延迟与体验取舍

一次返回少量候选通常比顺序请求三个结果少网络往返，但输出更长，而且用户选择本身会增加完成时间；不能据此保证总延迟更低。两阶段方案（先修改，发现歧义再请求候选）保留普通情况的速度，但歧义情况会多一次模型等待。具体耗时应单独实测，本次不把现有单结果请求耗时当成候选方案的性能数据。

建议下一步先做离线候选评测，证明候选覆盖率值得新增交互，再接选择浮窗。当前改动仅增强单结果纠错提示词。
